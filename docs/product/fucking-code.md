# Fucking Code

> 把 AI 研发团队变成你的乙方。

Fucking Code 是一个面向非专业开发者的多 Agent 研发工作台。你不需要懂 PRD、架构、接口契约或测试流程；你只需要在群聊里说出想解决的问题，剩下的由一支 AI 研发团队以乙方的方式接住：先问清楚，再给建议，必要时反驳你，最后把方案、代码、测试和变更证据交付出来。

它不是“让一个 AI 一次性生成一个项目”，而是把真实研发团队的协作方式搬进聊天室。

## 核心突破：聊天室不是界面，而是组织

Fucking Code 最重要的设计不是“多 Agent”，而是**共享聊天室**。

- 所有房间成员收到每条消息，拥有同一份对话历史；
- 每个 Agent 独立判断 `PASS` 或 `SPEAK`；
- 每轮只允许一个人把话说完，其他人下一轮再判断；
- 甲方是房间里的角色，团队可以问甲方、反驳甲方；
- Agent 可以问同事、交接问题；
- 对话可以直接创建任务、产物、审批和门禁，驱动真实工程状态；
- 房间记录持久化、可回放、可审计。

聊天室不是聊天入口，而是项目的控制平面。Agent 能力是变量，房间协议才是乘法。

---

## 1. 为什么需要它

大多数 AI 编程产品默认用户已经知道自己要什么：

- 一句话生成一个项目，需求浅、返工多；
- 多个 Agent 同时回复，信息噪声大，用户不知道该听谁；
- AI 无条件服从，不指出范围风险、技术债和更差的选择；
- 代码生成完就结束，没有验收、评审、合并和可追溯证据。

Fucking Code 反过来做：

- **用户是甲方，团队是乙方**，不是上下级指令关系；
- **每次只有一个人回复**，像真实会议一样轮流说话；
- **团队先澄清**目标、用户、场景、边界和成功标准；
- **允许问同事、问甲方、反驳甲方**，并给出理由和替代方案；
- **人工门禁**保留：产物要接受、代码要验收、合并要确认；
- 所有关键动作写入审计，代码有 worktree、Diff、测试和规格核对证据。

## 2. 产品原则

### 甲方 / 乙方

用户是群聊里的甲方/客户。AI 团队是乙方研发团队。

团队会：

- 先问清楚，而不是立刻开工；
- 对不合理需求说“不”，并解释为什么；
- 给出更小、更稳、更符合真实目标的替代方案；
- 在信息不足时主动追问，而不是编造假设；
- 在需要拍板时把问题交回甲方。

### 群聊，而不是路由器

所有房间成员都会收到每条消息，每个 Agent 独立判断：

- `SPEAK`：这与我的岗位有关，我能提供别人没有的信息；
- `PASS`：别人已经覆盖，或与我无关，沉默。

`@` 是注意力，不是访问权限。沉默是合法结果，并且会被记录原因。

### 单发言人

每一轮只允许一个 Agent 把话说完：

- 被 @ 或被交接的人优先；
- 当前阶段负责人优先；
- 其他想发言的人排队到下一轮；
- 避免多个 Agent 同时刷屏。

### 多轮澄清

需求不够清楚时，团队不会硬做：

- PM 先问目标用户、核心场景、成功标准、范围和非目标；
- 需要甲方拍板时使用 `ask_user`，本轮暂停等待；
- 甲方回答后继续下一轮；
- 可以问同事，也可以问甲方；
- 需求明确后才进入 PRD、方案和任务。

### 可反驳

团队不是无条件服从：

- 发现范围失控、体验变差或技术风险时直接指出；
- 必须给出理由、风险和替代方案；
- 由甲方决定是否接受，而不是 AI 替甲方做决定。

### 人工门禁

- PRD / 验收标准 / 技术方案需要接受；
- 代码任务必须通过测试和规格核对；
- 验收合并是人工动作；
- 阶段推进有门禁，强制推进需要理由并写入审计。

## 3. 一支完整的 AI 研发团队

| 角色 | 职责 |
|---|---|
| PM | 澄清需求、维护 PRD、验收标准、范围与非目标 |
| Architect | 模块边界、数据模型、接口契约、技术风险 |
| Lead | 拆任务、定依赖、排期、推进和收敛 |
| Frontend | 界面、交互状态、组件与前端测试 |
| Backend | API、数据、事务、幂等、迁移与后端测试 |
| QA | 测试策略、边界用例、回归和验收证据 |
| Security | 权限、越权、注入、密钥和供应链风险 |

每个角色有自己的提示词、模型配置、颜色和房间状态。你可以：

- 把 Agent 移出/加入房间；
- 指定下一条消息只让部分 Agent 参与；
- `@` 某个 Agent 把它拉进当前讨论；
- 让 Agent 之间 `@` 或 `handoff`，互相提问。

## 4. 一次完整的需求到交付

```text
甲方提出一个想法
  ↓
PM 先问清楚目标用户、场景、成功标准、边界
  ↓
甲方回答（可能多轮）
  ↓
PRD + 验收标准 → 甲方接受
  ↓
Architect 出方案和接口契约 → 甲方接受
  ↓
Lead 拆成可执行任务
  ↓
Backend / Frontend 在隔离 worktree 实现
  ↓
运行测试 + QA 规格核对
  ↓
甲方查看 Diff / 测试报告 / 规格核对
  ↓
验收合并到默认分支，或推送 PR
```

### 研发阶段

```text
intake → discovery → design → planning → build → test → review → deliver → done
```

每个阶段都有门禁：

- discovery：PRD 已接受 + 验收标准存在；
- design：技术方案已接受；
- planning：至少一个可执行任务；
- build：任务完成/取消；
- test：测试报告已接受；
- review：代码评审审批通过；
- deliver：交付审批通过。

## 5. 核心能力

### 聊天与澄清

- 共享聊天室、广播给所有房间成员；
- 单发言人、阶段负责人优先；
- `PASS / SPEAK` 自主判断；
- `ask_user` 暂停等待甲方；
- `@` / `handoff` 向同事提问；
- 多轮澄清，不急着一次性做完。

### 产品与工程产物

- PRD、验收标准、技术方案、API 契约、计划；
- Diff、测试报告、规格核对报告、长期记忆；
- 版本化、可接受/退回、可追溯来源消息。

### 任务与代码

- 任务看板、优先级、负责人、验收标准、依赖；
- 进入 build 后自动启动就绪任务（可在项目设置中关闭）；
- 每个任务完成后自动触发 QA/Lead 群聊回馈；
- 任务编辑/删除/取消/重试；
- 隔离 Git worktree；
- Agent 编码会话；
- 自动跑测试；
- QA 按任务验收标准做规格核对；
- 验收合并到默认分支；
- 配置 `GITHUB_TOKEN` 后推送并创建 GitHub PR。

### 协作与安全

- 项目成员角色：Owner / Member / Viewer；
- Viewer 全站只读；
- 在线成员 presence；
- 任务/项目乐观锁，避免覆盖；
- 自助修改密码；
- 项目、任务、产物、审批、阶段变更审计；
- 测试和终端命令通过 bubblewrap 沙箱执行；
- PGlite 备份/恢复脚本。

### 长期记忆

- Agent 可以提出记忆候选；
- 用户可以手工添加；
- 接受后注入群聊和代码任务提示词；
- 同类型同标题自动去重升版本；
- 180 天未使用自动衰减。

## 6. 工作台

三栏工作台：

- **左侧**：项目、团队聊天室、开发任务、代码/目录、需求与产物、运行活动、管理后台；
- **中间**：群聊、任务看板、产物列表、代码视图；
- **右侧**：团队名册、门禁/审批、运行状态、在线成员。

代码视图包含：

- 文件树；
- 仓库/工作区切换；
- 语法高亮；
- 文件级 Diff；
- 测试输出；
- 命令终端；
- 人工编辑（会重新打开验收）；
- 重新核对；
- 停止运行。

## 7. 技术架构

```text
apps/
  api/                 Hono API + SSE + Orchestrator
  web/                 SolidJS + Vite 工作台
packages/
  contracts/           共享类型、事件、状态
  domain/              角色提示词、动作协议、任务状态机、阶段门禁
  db/                  Drizzle + PGlite、迁移、seed、仓储
  agents/              群聊编排、注意力判断、动作应用
  workspace/           Git worktree、命令沙箱、编码 Agent、规格核对
data/
  pg/                  本地 PGlite 数据
  repos/               项目仓库
  worktrees/           隔离工作区
```

关键设计：

- **持久化事件流**：`events.seq` 是 SSE 恢复游标；
- **受控动作协议**：Agent 只能通过经过 zod 校验的 `devteam` JSON 动作块改变状态；
- **提示词不是权限边界**：服务端校验阶段、门禁、项目角色和任务状态；
- **代码隔离**：每个任务独立 worktree 和分支；
- **验收证据**：Diff、测试输出、规格核对、合并 commit 都可追溯。

## 8. 快速开始

### 依赖

- Node.js 22+
- Git
- Linux（推荐，bubblewrap 沙箱）
- 一个运行中的 OpenCode Server（可选，`AGENT_RUNTIME=mock` 可离线）

```sh
npm install
cp .env.example .env
npm run dev
```

打开 <http://127.0.0.1:5174>。

首次启动会创建：

- PGlite 数据库；
- 本地管理员和示例项目；
- Acme Notes 示例仓库。

### 生产构建

```sh
npm run build
NODE_ENV=production npm start
```

### 备份

```sh
npm run backup
npm run restore -- backups/xxx.tar.gz --force
```
