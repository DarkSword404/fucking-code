# 聊天室即组织：Fucking Code 的共享房间式多智能体研发范式

### —— 从“选择 Agent”到“组织一场有甲方在场的研发对话”

**工作论文（Design Paper）v0.2 · 2026-10-23**

> 一句话论证：Fucking Code 的真正突破不是“多 Agent”，而是“房间”。它把共享聊天室从聊天 UI 提升为研发的组织基础设施：所有成员共享同一份对话状态，每个成员独立判断是否发言，每轮只允许一个人把话说完，甲方作为房间里的角色参与澄清、质询和验收，对话本身可以直接驱动任务、产物、代码和门禁。Agent 能力是变量，房间协议才是乘法。

---

## 摘要

以 Trae、CodeBuddy/WorkBuddy、OpenCode 为代表的 Vibe Coding 产品，已经证明大模型可以在真实代码库中完成规划、编辑、运行和调试。它们持续增强 Agent 的能力，但大多数产品仍然把协作的基本单位理解为“一个用户与一个 Agent 的会话”，或者“多个 Agent 并行执行多个任务”。

本文提出一个不同的判断：**当 AI 从“生成代码”走向“推进项目”，真正的瓶颈不是 Agent 数量，而是组织方式。** 现有产品缺少的不是更强的模型，而是一个让多个角色、甲方、工程状态和交付证据共享同一上下文的“房间”。

Fucking Code 的核心设计正是这个房间：

- 所有房间成员收到每条消息（广播，而不是路由器挑人）；
- 每个 Agent 独立判断 `PASS` 或 `SPEAK`（沉默是合法结果）；
- 每轮只允许一个 Agent 发言（单声道轮流制）；
- Agent 可以问同事、问甲方；向甲方提问时本轮暂停；
- 用户以甲方/客户身份在场，而不是无条件指令源；
- 对话可以创建任务、产物、审批、交接，直接改变项目状态；
- 房间记录持久化、可回放、可审计，形成组织记忆。

本文的贡献是：

1. 提出“聊天室即组织”的房间中心视角，区分私密会话、路由器、并行面板、共享房间四种协作拓扑；
2. 给出房间的形式模型与五条不变量：广播、注意力、单声道、甲方在场、持久可行动；
3. 将 Fucking Code 的门禁、规格核对、worktree、合并、审计等机制解释为房间内的制度，而不是孤立功能；
4. 与 Trae、CodeBuddy/WorkBuddy、OpenCode 进行组织维度对比；
5. 给出以房间为中心的可检验命题和实验设计；
6. 明确边界：在规格明确、低延迟、深度 IDE 交互的任务上，专用 AI IDE/终端 Agent 仍然更优。

本文不主张 Fucking Code 在所有编码任务上优于现有产品。它主张的是一个条件性命题：**对于需求模糊、非专业用户主导、需要多角色判断和交付问责的项目，房间式组织比 Agent 式工具具有更高的适配度。**

**关键词**：共享聊天室；多智能体系统；Vibe Coding；人在回路；共同语境；发言秩序；软件工程治理；设计科学

## 1. 引言

过去两年，AI 编程产品的主线是提升“从自然语言到代码”的转化效率。第一代产品以补全和问答为主；第二代产品让 Agent 在 IDE 或终端中读取仓库、修改多文件、运行测试；第三代产品开始引入规划、子 Agent、并行任务、浏览器预览、部署和产物空间。

这条路线极大地提升了专业开发者的局部效率，但也暴露了一个结构性错位：

> **AI 编程工具默认用户知道自己要什么，而大量真实用户并不知道。**

非专业用户通常只能说出一个表层愿望：

- “我想做一个记账 App。”
- “帮我做一个客户管理系统。”
- “我要一个能自动发小红书的内容工具。”

如果系统立即开始生成 PRD、架构和代码，它实际上是把用户没有表达出来的假设，偷偷替换成了确定需求。项目可能“成功运行”，却没有解决用户真正的问题。

更严重的是，当多个 Agent 同时工作或同时发言时，用户很难判断：

- 现在是谁在负责？
- 这个方案是谁定的？
- 我不同意，应该找谁？
- 代码是谁改的？
- 测试通过是否等于需求满足？
- 出了问题能不能回滚？

现有产品通常分别优化了其中一部分：

- **AI IDE** 优化编辑体验、上下文和代码执行；
- **通用 Agent 工作台** 优化任务编排、工具调用和企业权限；
- **开源 Agent Runtime** 优化模型接入、会话、工具和可扩展性。

但它们大多仍然把“对话”当作**入口**：用户给 Agent 下指令，Agent 回到自己的会话里执行。对话不是组织本身，而是组织的输入框。

Fucking Code 的核心主张不同：

> **聊天室不是入口，而是组织。**
>
> 研发不是“选择一个 Agent 让它做”，而是“让甲方、PM、架构、开发、QA 在同一个房间里，按顺序把问题说清楚，并把说清楚的结果变成可验收的工程状态”。

这个判断带来一个关键的设计转向：

```text
Agent-centric:
  用户 → 选择一个 Agent → Agent 执行 → 返回结果

Room-centric:
  甲方 + 团队 → 共享房间 → 广播/判断/轮流发言 → 行动 → 项目状态
```

本文认为，后者才是 AI 研发产品在“非专业用户 + 模糊需求 + 多角色协作”场景中的真正突破。

本文用设计科学的方法论证这一范式，并诚实地界定它不适用于什么场景。

## 2. 研究背景：Vibe Coding 的三种产品谱系

### 2.1 从 Copilot 到 Agent Team

Vibe Coding 的早期形态是“对话 + 补全”：用户描述意图，模型生成代码片段。随后，Agent 开始获得工具权限，可以读写文件、运行命令、调用 MCP、打开浏览器。再往后，产品开始引入多 Agent、并行任务和长任务编排。

这带来一个容易被忽略的转变：

> 当 AI 从“补全一段代码”变成“推进一个项目”，产品的核心问题就从**生成质量**变成了**组织质量**。

组织质量包括：谁发言、谁决策、谁验收、谁负责、何时暂停、如何回滚。

### 2.2 Trae：AI IDE + SOLO Agent

Trae 是字节跳动的 AI 编程产品。根据其公开文档，当前 Trae 同时提供：

- IDE Mode：完整的 AI 编程环境，适合深度编辑和调试；
- Agent Mode：从想法到交付的任务编排，可管理多个项目、编排多个 Agent 并行推进任务；
- SOLO：更自主的编码 Agent，可规划、执行，并使用子 Agent 处理复杂任务；
- Artifacts：统一管理代码、HTML、文档、图片、报告等交付物；
- Plugins / Skills、远程 SSH、自动化任务、Hooks 等扩展能力。

Trae 的设计中心是**开发者生产力与任务吞吐**：让一个开发者或一个小团队，用多个并行 Agent 更快地把任务做完。

这非常有效，但它与 Fucking Code 解决的问题并不完全相同。Trae 的并行 Agent 主要解决“多个任务同时推进”；Fucking Code 的单发言人解决的是“多个角色如何在同一个问题上形成有序判断”。前者是吞吐问题，后者是组织问题。

### 2.3 WorkBuddy / CodeBuddy：企业 Agent 工作台与编码 Agent

腾讯云的 CodeBuddy / WorkBuddy 代表了另一条路线：把 AI 编程、办公自动化和企业 Agent 平台结合起来。

公开资料显示，CodeBuddy 提供 IDE、插件和 CLI 形态，支持 Plan Mode、多 Agent 并行、MCP、Skills、Rules、沙箱执行等能力；WorkBuddy 则定位为桌面/企业 Agent 工作台，强调文档、表格、研究、沟通等知识工作，以及企业权限、审计和托管 Agent。

这条路线在**企业集成、权限、沙箱和办公场景**上很强。它把 Agent 放进企业工具链，而不是只放在编辑器里。

但从公开产品叙事看，它的核心仍然是“Agent 完成任务”与“企业统一管控”；它并没有把“甲方作为群聊中的角色、由乙方团队多轮问询并可以反驳甲方”作为产品的一级交互协议。

### 2.4 OpenCode：开放的 Agent Runtime

OpenCode 是开源 AI 编程 Agent，提供终端、桌面和 IDE 形态，支持大量模型提供商、会话、工具、权限、子 Agent、LSP 和 HTTP API。

OpenCode 的价值在于**可编程的 Agent 基础设施**：它把模型、工具、会话、权限和客户端解耦，允许其他产品在其上构建。

Fucking Code 实际上把 OpenCode 作为编码运行时使用。这意味着二者不是替代关系，而是**应用层与运行时层**的关系：

- OpenCode 提供“一个 Agent 如何执行”；
- Fucking Code 提供“一支团队如何组织、质询、验收和交付”。

### 2.5 共同缺口

将三者放在一起看，可以发现一个共同缺口：

| 产品谱系 | 最擅长 | 相对缺口 |
|---|---|---|
| AI IDE / SOLO | 代码编辑、任务编排、并行吞吐、预览部署 | 甲方角色、多轮需求问询、组织级门禁与交付问责 |
| 企业 Agent 工作台 | 企业权限、工具集成、办公自动化、沙箱 | 软件研发角色组织、单声道讨论、规格验收闭环 |
| 开源 Agent Runtime | 模型无关、可扩展、会话与工具 | 产品级流程、角色、门禁、审计与客户关系 |

Fucking Code 的机会不在于“比它们多一个按钮”，而在于补上**组织层**。

## 3. 核心突破：聊天室不是界面，而是组织

### 3.1 四种协作拓扑

要理解 Fucking Code 的差异，不能只看“有没有多 Agent”，而要看**对话的拓扑结构**。

| 拓扑 | 典型形态 | 对话状态 | 跨 Agent 可见性 | 发言秩序 | 甲方位置 | 主要失效模式 |
|---|---|---|---|---|---|---|
| 私密会话 | AI IDE / 单 Agent 终端 | 单线程、私有 | 无 | 单声道 | 会话外 | 隐藏上下文、重复劳动、决策不可见 |
| 路由器 | “让 PM/架构师来回答” | 用户→调度器→单个 Agent | 低/不可见 | 调度器决定 | 会话外 | 电话游戏、责任转移、上下文丢失 |
| 并行面板 | 多 Agent 同时回答/并行任务 | 多线程或共享提示 | 部分可见 | 无/并行 | 会话外 | 刷屏、重复、观点互相覆盖 |
| 共享房间 | Fucking Code | 持久、共享、可回放 | 全部成员可见 | 单声道轮流 | 房间内的甲方角色 | 协调开销、延迟、需要好的发言协议 |

这张表揭示了本文的核心观点：

> 多 Agent 并不自动产生团队能力。  
> 只有当 Agent 共享同一个对话状态，并遵循一套发言与行动协议时，多 Agent 才会变成组织。

Trae 的 SOLO/Agent Mode 主要优化“任务并行吞吐”；WorkBuddy/CodeBuddy 主要优化“Agent 完成企业任务”；OpenCode 主要优化“单个 Agent 的可编程运行时”。它们都可以很强，但它们的默认拓扑不是“一个所有角色和甲方共享的、有序的、可行动的研发房间”。

### 3.2 房间的五条不变量

Fucking Code 的房间不是普通的群聊。它必须同时满足五条不变量：

**I1 广播（Broadcast）**  
每条消息广播给所有房间成员，而不是由路由器只发给一个 Agent。所有成员拥有同一份对话历史。

**I2 注意力而非访问权（Attention, not access）**  
`@` 只提高某人的注意力，不改变谁能看到消息。未被 @ 的成员仍然读到并可以决定发言。

**I3 单声道（Single speaker）**  
每一轮只允许一个 Agent 把话说完。其他想发言的人排队到下一轮，重新阅读后再判断。

**I4 甲方在场（Client presence）**  
用户不是外部指令源，而是房间里的甲方角色。团队可以问甲方、反驳甲方；甲方也可以质询团队。

**I5 持久且可行动（Durable and actionable）**  
房间记录持久化、可回放；消息可以携带受控动作，直接创建任务、产物、审批或交接，改变项目状态。

这五条不变量缺一不可：

- 缺 I1：Agent 各自为战，出现“电话游戏”；
- 缺 I2：`@` 变成权限，房间退化为路由器；
- 缺 I3：多 Agent 同时刷屏，用户无法跟上；
- 缺 I4：团队变成无条件执行的工具，需求错配被放大；
- 缺 I5：聊天只是聊天，无法形成可验收的工程交付。

### 3.3 房间的形式模型

可以将 Fucking Code 的房间定义为一个七元组：

```text
R = (P, H, A, Π, S, E, G)
```

其中：

- `P`：参与者集合，包括 Agent 角色和甲方；
- `H`：持久化消息历史；
- `A`：注意力函数，决定每个成员是否认为消息与自己相关；
- `Π`：发言协议，包括单声道、优先级、排队和暂停；
- `S`：项目状态，包括产物、任务、代码、审批和阶段；
- `E`：持久事件日志；
- `G`：制度约束，包括角色权限、门禁和人工批准。

一个回合可以形式化为：

```text
m_t = Broadcast(H_t)
∀p ∈ P: d_p = A(p, H_t) ∈ {PASS, SPEAK}
s = Select(Π, {p | d_p = SPEAK})
r_t = Speak(s, H_t)
S_{t+1} = Apply(r_t, S_t)
H_{t+1} = H_t ∪ {r_t}
E_{t+1} = E_t ∪ {event(r_t, S_{t+1})}
```

其中 `Select` 满足单声道约束：

```text
|s| = 1
```

如果发言人向甲方提出 `ask_user`，则：

```text
Π.pause() until 甲方回复
```

这个模型说明：**房间不是消息的容器，而是一个把对话转化为项目状态的状态机。**

### 3.4 为什么房间能产生能力突破

房间的价值不是“看起来像群聊”，而是它同时提供了五种组织能力。

#### 共同语境（Common ground）

Clark 与 Brennan 的“共同基础”理论指出，协作需要参与者不断确认彼此的理解。共享房间让所有成员看到同一份历史，减少“我以为你知道”的隐含假设。

在私密会话或路由器中，Agent 只看到被转述的部分上下文；在共享房间里，PM 的追问、架构师的反对、QA 的质疑都留在同一份记录中，后续成员可以基于完整语境行动。

#### 发言秩序（Turn-taking）

Sacks、Schegloff 与 Jefferson 的会话分析表明，轮流发言是对话可理解性的基础。多个 Agent 同时输出，会破坏指代、回应和责任的连续性。

Fucking Code 的单声道协议把“多 Agent”从并行面板变成有序会议：一个人说完，下一个人基于这句话回应，而不是各自对着同一个提示词自说自话。

#### 言语行为（Speech acts）

Austin 和 Searle 把“说话”视为一种行动：提问、承诺、批准、拒绝，都会改变社会状态。

Fucking Code 把这一点工程化：Agent 的消息可以携带 `create_task`、`create_artifact`、`ask_user`、`handoff`、`request_approval` 等动作。房间里的“说”会变成项目状态里的“做”。

#### 共享工作空间意识（Workspace awareness）

Dourish 与 Bellotti 指出，协作不仅依赖任务分配，还依赖参与者对彼此活动、上下文和状态的持续感知。Malone 与 Crowston 则把协调视为对依赖关系的管理。

共享房间把“谁在读、谁在说、谁在等、谁被问”变成所有成员可见的状态。这降低了隐式依赖带来的重复劳动和等待，也让甲方能看到团队正在处理哪一部分问题。

#### 组织记忆（Organizational memory）

房间记录持久化并可回放，使项目拥有可追溯的组织记忆：谁在什么时候提出了什么、依据是什么、谁批准了、代码从哪来。

这把“聊天记录”从临时 UI 提升为**审计与恢复的基础设施**。

### 3.5 房间是控制平面，不是聊天 UI

在 Fucking Code 中：

- 聊天室是**控制平面**：决定做什么、谁来做、何时暂停、是否接受；
- 产物、任务、代码是**数据平面**：承载被决定后的工程结果；
- 事件日志与审计是**证据平面**：证明决定如何发生。

这类似于操作系统中的控制平面与数据平面分离：

```text
Room (control plane)
  ├── decisions / questions / handoffs / approvals
  ↓
Project state (data plane)
  ├── artifacts / tasks / worktrees / diffs / tests
  ↓
Event log (evidence plane)
  └── replay / audit / recovery
```

这也是为什么 Fucking Code 的聊天室不能被简单理解为“一个聊天页面”。它是整个系统的组织内核。

### 3.6 房间避免的失败模式

| 失败模式 | 传统形态 | 房间如何避免 |
|---|---|---|
| 隐藏上下文 | 每个 Agent 私有会话 | 广播 + 持久历史 |
| 电话游戏 | 路由器转述 | 所有成员直接读原文 |
| 多 Agent 刷屏 | 并行面板 | 单声道轮流 |
| 需求臆测 | 一次性生成 | 甲方在场 + `ask_user` 暂停 |
| 无条件迎合 | 用户即指令 | 乙方角色 + 可反驳协议 |
| 测试通过但规格不满足 | 测试即完成 | 规格快照 + QA 核对 |
| 决策不可追溯 | 聊天记录丢失 | 持久事件 + 审计 |
| 变更不可逆 | 直接改主分支 | worktree + 内部评审合并 |

## 4. 评价框架

本文提出九维评价框架。它评价的不是模型智商，而是产品如何组织人与 Agent 完成一次可验收的研发。

### 维度定义

| 维度 | 核心问题 |
|---|---|
| D0 共享房间 | 是否所有角色与甲方共享同一份持久、可行动的对话状态？ |
| D1 需求澄清 | 系统是否主动把模糊需求变成可验证目标？是否允许甲方多轮回答？ |
| D2 角色分工 | 是否有稳定的岗位、职责和专业视角，而不是一个通用 Agent？ |
| D3 发言秩序 | 多角色如何轮流发言？是并行面板、路由器，还是单声道共享房间？ |
| D4 甲方在场 | 用户是否被建模为甲方/客户，而不是无条件指令源？ |
| D5 规格验收 | 是否把验收标准作为合同，而不只是“测试通过”？ |
| D6 变更治理 | 代码是否隔离、可审查、可回滚、可合并？ |
| D7 人工门禁 | 关键产物、阶段和合并是否保留人类批准？ |
| D8 可追溯性 | 谁在何时做了什么、依据是什么，是否可审计？ |

### 评价符号

- ● 明确作为核心能力；
- ◐ 部分具备、可配置或依赖外部流程；
- ○ 公开资料未体现为一级能力；
- — 不适用或不是同类产品。

> 说明：比较基于 2026-10-23 可访问的官方公开资料与产品文档，不评价未公开的内部能力，也不以模型 benchmark 代替产品设计分析。

## 5. Fucking Code 的设计

### 5.1 设计原则

Fucking Code 将自身定义为“AI 乙方研发团队”，而不是“更聪明的代码生成器”。其设计原则可以概括为八条：

1. **甲方在场**：用户是客户，不是命令源；团队可以问、可以反驳。
2. **广播而非路由**：所有房间成员收到每条消息，各自判断是否发言。
3. **单声道发言**：每一轮只有一个人把话说完，避免多人同时输出。
4. **角色异质**：PM、Architect、Lead、Frontend、Backend、QA、Security、DevOps 各自有职责边界。
5. **规格即合同**：任务绑定已接受的 PRD 和验收标准，测试通过不等于规格满足。
6. **门禁即制度**：AI 判断阶段、服务端校验门禁后内部推进；阶段图允许回退与迭代。甲方只处理产品决策；技术产物、代码评审与合并由团队内部 QA/Lead 按证据批准。
7. **变更即候选**：代码先进入隔离 worktree，通过验收后才进入主分支。
8. **证据优先**：Diff、测试报告、规格核对、审计记录优先于 Agent 的自我声明。

### 5.2 甲方 / 乙方：把用户建模为“客户”

传统 AI 编程产品的隐含模型是：

```text
用户 = 指令发出者
AI = 指令执行者
```

Fucking Code 的模型是：

```text
用户 = 甲方 / 客户
AI 团队 = 乙方 / 研发组织
```

这不是称呼变化，而是行为约束：

- 需求不清楚时，乙方应该问，而不是猜；
- 方案有风险时，乙方应该指出，而不是迎合；
- 范围失控时，乙方应该给更小的替代方案；
- 需要拍板时，乙方应该把决策交回甲方；
- 甲方说“你决定”时，乙方可以给默认方案，但必须写清假设。

代码层面，这一原则体现在：

- `buildSystemPrompt` 和 `buildPrompt` 明确写入甲方/乙方关系；
- PM 的提示词从“最多一轮澄清”改为“可以多轮澄清”；
- 所有角色都可以使用 `ask_user`；
- `ask_user` 会暂停本轮，等待甲方回答，而不是团队继续自说自话；
- 任何角色都可以 `@` 同事或 `handoff`，把问题交给更合适的人。

### 5.3 共享房间 + 广播 + 单声道

Fucking Code 保留了“群聊”的核心语义：

- 所有房间成员都能读到每条消息；
- 每个 Agent 独立判断 `SPEAK` 或 `PASS`；
- 沉默是合法结果，并记录原因；
- `@` 是注意力，不是访问权限。

但与传统多 Agent 并行发言不同，它增加了**单声道轮流制**：

- 每轮只选一个发言人；
- 被 @ 或被交接的人优先；
- 当前阶段负责人优先；
- 其他想发言的人排队到下一轮；
- 发言人说完后，所有人重新阅读、重新判断。

这解决了一个关键问题：

> 多 Agent 的价值来自不同视角，但多 Agent 的失败往往来自同时说话。

单声道不是减少信息，而是把信息按时间顺序组织起来，让用户能跟上，也让后续 Agent 能基于前一个人的完整发言作出判断。

### 5.4 问询、质询与反驳

Fucking Code 把“问”作为一等动作：

- **问甲方**：`ask_user`，本轮暂停；
- **问同事**：`@role` 或 `handoff`，被问者下一轮优先；
- **质询方案**：任何角色都可以指出风险、范围蔓延、技术债；
- **反驳甲方**：必须给出理由、风险和替代方案。

这使系统从“需求执行器”变成“需求共同定义者”。

一个典型回合是：

```text
甲方：我想做一个记账 App。
PM：这个范围太大。先确认目标用户、成功标准和数据来源。
    （ask_user）
[本轮暂停]
甲方：个人自用，主要记录日常消费，希望坚持 7 天。
PM：那这一版只做手动记账 + 月度分类汇总，不做多人共享和账单 OCR。
    （提出更小的 MVP）
```

这比“直接生成一个记账 App”更可能得到真实可用的产品。

### 5.5 规格即合同

Fucking Code 的代码任务不是“让 Agent 改代码然后跑测试”，而是：

1. 任务创建时捕获当前已接受的 PRD、验收标准和契约版本；
2. 编码 Agent 的提示词包含完整规格；
3. 代码完成后运行测试；
4. QA Agent 再按**任务验收标准**做规格核对；
5. 测试通过但规格不满足，任务仍然失败；
6. 只有测试和规格核对都通过，任务才进入 review。

这把“验收标准”从文档里的愿望，变成了任务执行的合同。

### 5.6 变更治理：worktree、验收、合并

代码变更进入隔离的 Git worktree 和分支，不直接影响主仓库。

- 人工可以查看文件树、Diff、测试输出；
- 人工可以编辑文件，编辑会使任务回到 `in_progress` 并需要重新核对；
- 规格核对通过后，由团队内部评审自动合并；
- 合并记录 commit、分支、操作者和时间；
- 也可以推送分支并创建 GitHub PR；
- 删除任务/项目会清理 worktree 和分支；
- 测试/终端命令在 bubblewrap 沙箱中执行。

这使 AI 变更成为“候选变更”，而不是不可逆的现实。

### 5.7 权限、审计与记忆

Fucking Code 把组织制度写进代码：

- Owner / Member / Viewer 三种项目角色；
- Viewer 只读，后端也不允许绕过；
- 阶段门禁和人工审批；
- 审计事件记录关键动作；
- 在线成员 presence；
- 任务/项目乐观锁；
- 长期记忆必须被接受后才注入；
- 记忆去重、版本化和 180 天衰减；
- 备份/恢复脚本。

这些机制不是“企业功能堆料”，而是让 AI 团队的行为可解释、可追责、可恢复。

### 5.8 敏捷阶段：AI 判断，内部评审，允许循环

线性阶段图隐含一个错误假设：研发会沿着需求 → 设计 → 开发 → 测试一路向前。真实敏捷
研发经常在测试失败后回到开发、在评审发现问题后回到方案或开发、在交付后开始下一轮需求。

Fucking Code 因此把阶段设计成**有门禁的图**，而不是固定流水线：

- AI 根据产物接受、任务完成、测试证据等判断是否该进入、回退或开始新一轮；
- AI 通过 `request_phase` 发起阶段判断，说明目标阶段和理由；
- 服务端校验合法性和门禁后内部推进，并记录内部评审审计；
- 前进必须满足当前阶段门禁；回退和迭代循环不需要伪造“已完成”的证据；
- 阶段内部推进后自动开发仍然暂停，甲方要明确点「继续自动开发」才会跑任务；
- 负责人保留手动推进作为兜底，但存在待决策项时不可用。

这把“敏捷”从口号变成房间协议：AI 有判断权，内部 QA/Lead 有评审权，服务端有校验权，审计有记录权。

### 6.1 定性比较

### 6.2 七条可检验命题

**P1（共同语境）**  
广播式共享房间比私密会话或路由器转述更能提高跨角色共同语境，降低“电话游戏”和隐含假设。

**P2（发言秩序）**  
单声道轮流制比并行多 Agent 输出更能降低用户认知负荷，同时不会显著减少全轮次覆盖的关注点。

**P3（甲方在场）**  
把甲方作为房间角色、允许团队多轮 `ask_user` 并暂停，比一次性自主生成更能降低需求错配和返工。

**P4（对话即行动）**  
允许消息携带受控动作、直接驱动任务/产物/门禁的房间，比纯聊天或纯任务面板更能形成可验收交付。

**P5（持久记忆）**  
持久、可回放的房间记录比临时聊天记录更能支持审计、恢复和组织记忆；经过审核/去重/衰减的长期记忆更能降低上下文污染。

**P6（角色异质）**  
固定岗位 + 明确职责 + 同事问询/交接，比单一通用 Agent 产生更高质量的关键问题和更完整的风险覆盖。

**P7（边界条件）**  
对于规格明确、单文件、低延迟或强 IDE 交互的任务，专用 AI IDE / 终端 Agent 的单位时间效率更高；Fucking Code 应通过集成而非替代来发挥作用。

P7 是本文最重要的“反命题”。一个设计理论如果不能在边界条件下承认自己不适用，它就只是营销。

### 6.3 为什么这是“房间优势”，不是“模型优势”

Fucking Code 可以使用与竞品相同或不同的模型。它的差异主要来自：

- 房间拓扑：广播、共同语境、单声道、甲方在场；
- 交互协议：谁先说、谁后说、何时暂停；
- 角色结构：谁负责提问、谁负责实现、谁负责验收；
- 制度约束：什么情况下不能继续；
- 证据结构：什么算完成；
- 组织形式：用户以什么身份参与。

因此，即使底层模型完全相同，Fucking Code 与单 Agent 产品的行为也会显著不同。这使得它的优势可以被设计实验检验，而不是只能归因于“模型更强”。

## 7. 讨论

### 7.1 适用场景

Fucking Code 更适合：

- 非专业用户把模糊想法变成软件；
- 需求需要多轮澄清的产品从 0 到 1；
- 需要产品、架构、前后端、QA 多角色判断的项目；
- 需要人工审批、审计和可回滚交付的组织；
- 想把 AI 研发过程沉淀为组织能力的团队。

### 7.2 不适用或需集成

Fucking Code 不应声称在所有场景优于现有产品：

- 规格明确的单文件修改：AI IDE 的编辑体验更好；
- 极低延迟的编码循环：终端 Agent 更直接；
- 巨型 monorepo 的索引与重构：专用 IDE 更强；
- 需要丰富可视化调试、断点、性能剖析：IDE 更成熟；
- 需要企业级 SSO、Postgres RLS、容器配额：仍需基础设施补齐。

一个成熟的产品策略不是“取代 Trae/OpenCode”，而是：

```text
Fucking Code = 组织层
OpenCode / IDE = 执行层
GitHub / CI = 交付层
```

### 7.3 代价

这种设计不是免费的：

- 单发言人会增加墙钟时间；
- 多轮问询会增加 token 成本；
- 角色和门禁会增加操作步骤；
- 非专业用户需要学习“甲方如何回答”；
- 多 Agent 的上下文管理更复杂；
- 产品目前仍缺少 token 级流式输出、PostgreSQL RLS、编码 Agent 容器化。

论文主张的是“在目标场景下更适配”，不是“在所有指标上更优”。

## 8. 评估设计

### 8.1 研究问题

- RQ1：甲方在场 + 多轮问询是否降低需求错配？
- RQ2：单发言人是否降低认知负荷而不损失信息覆盖？
- RQ3：角色异质是否提升关键问题与风险覆盖？
- RQ4：规格验收与门禁是否降低验收争议和缺陷逃逸？
- RQ5：隔离变更与审计是否提升可逆性和信任？
- RQ6：在哪些任务上，专用 IDE/Agent 仍然更优？

### 8.2 实验条件

建议采用混合方法：

1. **受控实验**：24–36 名参与者，其中一半非专业用户；每人完成 4–6 个模糊需求任务。
2. **对照条件**：
   - Trae SOLO / Agent Mode；
   - CodeBuddy/WorkBuddy；
   - OpenCode + 手工流程；
   - Fucking Code。
3. **任务类型**：
   - 浅层需求（一句话想法）；
   - 冲突需求（范围/预算/时间冲突）；
   - 受监管需求（权限/审计）；
   - 明确的小任务（边界条件）。
4. **测量**：
   - 需求错配评分（盲评）；
   - 验收标准通过率；
   - 返工任务数；
   - 首次可验收交付时间；
   - 人工干预次数；
   - 每轮消息数/发言人熵；
   - 关键问题覆盖率；
   - 缺陷逃逸率；
   - 审计完整率；
   - token/费用/墙钟时间；
   - 主观认知负荷（NASA-TLX）和信任度。
5. **现场研究**：在真实小团队中部署 4–8 周，记录采用率、放弃率和协作模式。
6. **质性访谈**：重点访谈非专业用户，理解“什么时候觉得团队在问对问题”。

### 8.3 可证伪预测

- 若 P1 成立，Fucking Code 的“需求错配评分”应显著低于一次性生成条件。
- 若 P2 成立，单发言人条件的认知负荷应显著更低，而全轮次关注点覆盖不应显著下降。
- 若 P3 成立，角色团队应提出更多跨岗位关键问题。
- 若 P4 成立，规格核对应降低“测试通过但验收失败”的比例。
- 若 P7 成立，在明确小任务上，IDE/终端 Agent 的完成时间应更短。

如果实验发现 Fucking Code 只是在“更慢地得到相同结果”，那么本文的核心主张应被修正。

---

## 9. 效度威胁与局限

1. **尚未完成对照实验**：本文是设计论证，不是已完成的随机对照研究。
2. **模型混杂**：不同产品使用不同模型，难以完全隔离“设计效应”和“模型效应”。
3. **产品差异**：Trae/WorkBuddy/OpenCode 不是完全同类产品，比较维度需要谨慎。
4. **任务选择偏差**：模糊需求任务可能天然有利于多轮澄清。
5. **新奇效应**：参与者可能因为新交互而高估体验。
6. **实现成熟度**：Fucking Code 仍是 v0.2，工程稳定性、性能和生态不如成熟商业产品。
7. **安全边界**：编码 Agent 仍运行在宿主进程；bubblewrap 只隔离测试/终端命令；PostgreSQL RLS 尚未实现。

## 10. 结论

Fucking Code 的设计价值不在于“又做了一个 AI 编程工具”，而在于它把**聊天室**放到了架构中心：

1. **聊天室不是界面，而是组织。** 所有成员共享同一份持久对话状态，房间是项目的控制平面。
2. **多 Agent 需要发言秩序。** 广播保证共同语境，单声道保证可理解性，轮流保证责任连续。
3. **甲方必须在场。** 用户不是指令源，而是可以被问询、被反驳、也可以拍板的客户。
4. **对话必须能变成行动。** 消息驱动任务、产物、审批、代码和门禁，而不是停留在聊天记录里。
5. **行动必须留下证据。** 持久事件、规格核对、审计和可逆的 worktree 让交付可追溯。

在“非专业用户的模糊需求 → 可验收软件”这一目标函数上，Fucking Code 通过房间协议、单声道、甲方在场、角色问询、规格合同、阶段门禁、worktree 隔离、人工验收和审计，构造了一种比单 Agent 自主执行更完整的社会技术设计。

它不是要取代 Trae 的 IDE、WorkBuddy 的企业工作台或 OpenCode 的运行时；它要补上它们之间缺失的**房间层**。

> **Agent 决定团队能写多快，房间决定团队是否在做对的事。**
>
> Fucking Code 押注的是后者。

## 附录 B：论文性质声明

本文是**设计科学工作论文（design paper）**，不是已经完成的大规模实证研究。它的目的是：

- 明确 Fucking Code 的设计主张；
- 把主张转化为可检验命题；
- 给出与现有产品的可比较维度；
- 为后续用户实验和现场研究提供框架。

任何“优于”的结论都应被理解为**在特定目标函数和边界条件下的设计适配性**，而不是对模型能力或所有编码任务的普遍断言。
